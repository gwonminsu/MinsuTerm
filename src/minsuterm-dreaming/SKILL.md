# minsuterm-dreaming: 기억 유지보수 (수면)

목표는 많이 저장하는 것이 아니라, **정확한 정보를 필요한 순간에 회상할 수 있게 유지하는 것**이다.
대상은 현재 프로젝트의 Auto Memory 하나뿐이다.

사용자가 지정한 초점: $ARGUMENTS
(비어 있으면 현재 프로젝트의 기억 전체를 대상으로 한다.)

이 스킬은 MinsuTerm이 설치했다. `dreaming` 스킬과 절차가 같고 다른 점은 셋이다.

- 정합성 검사 스크립트가 Python이 아니라 Node(`scripts/check_memory.mjs`)로 돈다. Node가 없는 컴퓨터에서는 MinsuTerm이 대신 Node를 제공한다.
- 수면 제안 규칙이 사용자의 `CLAUDE.md`가 아니라 이 스킬 안에 있다(4절).
- `minsuterm-progress`의 자러 가기와 이어진다(5절).

같은 컴퓨터에 `dreaming` 스킬도 있으면 한 번의 수면에는 둘 중 하나만 실행한다.

## 0. 시작 전 확인

다음 중 하나라도 해당하면 메모리를 건드리지 않고 멈춘다.

- **사용자가 수면을 지시하지 않았다.** Claude가 스스로 필요하다고 판단해 이 스킬을 불렀다면 실행하지 않는다. 대신 한 줄로 제안만 하고 답을 기다린다.
  예: "중요한 정보가 많이 쌓여서 기억을 정리하고 자는 게 좋겠어요. 수면할까요?"
  - MinsuTerm 진행도 페이지에서 누른 **자러 가기**는 사용자의 직접 지시다.
- **사람의 수면에 대한 질문이었다.** 스킬을 중단하고 그 질문에 답한다.
- **진행 중인 작업이 있다.** 실행 중인 빌드나 테스트, 백그라운드 작업, 끝나지 않은 편집이 있으면 수면을 강행하지 않는다. 지금 하던 작업을 먼저 마칠지 사용자에게 묻는다.
- **Auto Memory가 꺼져 있다.** 시스템 프롬프트에 Memory 섹션이 없거나 `autoMemoryEnabled`가 `false`이면 그 사실만 알리고 끝낸다.

## 1. 범위와 금지 사항

**메모리 위치 확인 (하드코딩하지 않는다)**

1. 시스템 프롬프트의 Memory 섹션에 적힌 디렉터리를 쓴다. 이것이 가장 정확하다.
2. 그런 안내가 없으면 `~/.claude/projects/<project>/memory/`에서 찾는다. `<project>`는 git 저장소 루트로 정해지고, 저장소가 아니면 작업 디렉터리 경로로 정해진다. 경로 구분자와 `:`는 `-`로 바뀐다. 예: `C:\workspace\app` → `C--workspace-app`
3. 경로가 확실하지 않으면 쓰기 전에 사용자에게 묻는다.

**하지 않는 것**

- 다른 프로젝트의 메모리 디렉터리 수정
- 소스코드, 설정 파일, `CLAUDE.md` 수정. 바꿀 필요가 보이면 제안만 한다.
- git commit, push, branch, stash 등 git 상태 변경
- 외부 서비스나 다른 지식 저장소(Notion, 문서 도구, 클라우드 메모리 등)에 기록. 사용자가 따로 지시한 경우만 예외다.
- 비밀번호, API 키, 토큰, 개인 키 같은 비밀 정보 저장. 기존 기억에서 발견하면 제거를 제안한다.
- 사용자 확인 없는 파일 삭제와 대규모 구조 변경
- 근거 없는 내용을 추측으로 채우는 것. 접근할 수 없는 과거 대화를 근거로 사실을 만들지 않는다.
- 하지 않은 분석이나 검증을 했다고 보고하는 것

## 2. 기억 형식

- **세션에 정해진 형식이 우선이다.** 시스템 프롬프트의 Memory 섹션이 형식을 정해 두었다면 그대로 따른다. 2026-11 현재 Claude Code의 형식은 다음과 같다.
  - 파일 하나에 사실 하나를 담는다.
  - frontmatter에 `name`, `description`, `metadata.type`을 둔다. `type`은 `user`, `feedback`, `project`, `reference` 중 하나다.
  - `feedback`과 `project` 기억에는 `**Why:**`와 `**How to apply:**` 줄을 붙인다.
  - `MEMORY.md`는 한 줄짜리 포인터만 모은 색인이다.
- **기존 구조를 존중한다.** 디렉터리가 이미 다른 구조(예: 주제별 큰 파일)를 쓰고 있으면 그 구조를 유지한다. 구조를 바꾸자는 건 제안만 한다.
- **주제별 배치:** 파일 이름은 `<type>_<topic>.md` 형태로 짓는다(예: `project_auth-design.md`, `feedback_testing.md`). 관련된 기억끼리는 본문에서 `[[name]]` 링크로 잇는다.
- **확정과 검토 구분:** 확정된 사실은 그대로 적는다. 불확실한 내용은 본문 첫 줄에 `**상태:** 검토 중`, `가설`, `미확인` 중 하나를 쓰고 근거를 적는다.
- **변경 이력:** 결정이 바뀌면 지우고 새로 쓰지 않는다. 현재 결정을 본문 위에 두고, 그 아래에 이력을 한 줄씩 남긴다.
  예: `**이력:** 2026-11-23 Redis → Postgres 큐로 변경 (운영 부담 감소)`
  근거로서 가치가 남아 있는 이력은 오래되어도 지우지 않는다.
- **날짜:** "어제", "지난주" 같은 상대 날짜는 절대 날짜로 바꿔 적는다.
- **`MEMORY.md`는 색인으로만 쓴다.** 한 줄에 하나씩 `- [제목](file.md) — 한 줄 요약` 형태로 적고 본문 내용은 넣지 않는다.
  세션을 시작할 때 처음 200줄(또는 25KB)만 로드되므로 150줄이 넘으면 통합할 항목을 찾는다. 항목이 많으면 type별 소제목으로 묶는다.

## 3. 실행 절차

### 1단계: 현재 상태 조사

1. 현재 프로젝트(작업 디렉터리, git 루트)와 메모리 디렉터리를 확인한다.
2. `MEMORY.md`와 디렉터리 안의 `.md` 파일 목록을 확인한다.
   - 파일이 많으면 frontmatter의 `description`부터 읽는다.
   - 이번 세션과 관련 있거나 충돌할 수 있는 파일은 끝까지 읽는다.
3. 이번 세션에서 미래 세션에 쓸모 있는 정보를 **회상(Recall)**한다. 후보마다 근거(대화의 어느 부분, 어느 파일)를 붙인다.
   - 사용자 요구사항, 선호, 작업 방식 피드백(교정과 칭찬 모두)
   - 기술 설계와 아키텍처, 의사결정과 그 근거
   - 발생한 문제와 해결 과정, 실패한 시도와 재발 방지책
   - 진행 상황, 미해결 문제, 다음 작업
   - 외부 자료 위치(문서 URL, 대시보드, 티켓)
   - 기존 기억과 충돌하거나 바뀐 사항
4. 다음은 저장하지 않는다.
   - 코드, git 이력, `CLAUDE.md`만 봐도 알 수 있는 내용
   - 이번 대화에서만 의미 있는 내용, 잡담, 일회성 테스트 결과
   - 비밀 정보
5. 컨텍스트가 압축되어 앞부분이 요약으로만 남아 있다면, 요약에 있는 내용만 근거로 쓴다. 사라진 세부는 추측하지 않는다.

### 2단계: 기억 비교 (Verify)

후보를 기존 기억과 하나씩 대조해 판정한다.

| 판정 | 기준 | 처리 |
| --- | --- | --- |
| 신규 | 기존에 없고 미래 세션에 유용함 | 추가 |
| 중복 | 같은 사실이 여러 곳에 있음 | 하나로 병합 |
| 보완 | 기존 기억에 세부나 근거가 빠져 있음 | 보완 |
| 변경 | 결정이나 사실이 바뀜 | 수정하고 이력을 남김 |
| 노후 | 더 이상 유효하지 않아 보임 | 근거가 있으면 수정, 삭제는 사용자 확인 후 |
| 충돌 | 현재 상태와 기억이 다름 | 확인할 수 있으면 확인하고, 못 하면 `검토 중`으로 표시 |
| 불확실 | 근거가 부족함 | 저장을 보류하거나 `검토 중`으로 표시 |

**검증 방법**

- 기억이 파일, 함수, 플래그, 경로를 가리키면 Glob/Grep/Read로 실제로 있는지 확인한다. 이때 프로젝트 파일은 읽기만 한다.
- 확인하지 못한 것은 `미확인`으로 남긴다.

**중요도 판단**

이 정보를 모르면 다음 세션의 Claude가 실수하거나 사용자에게 같은 것을 다시 묻게 되는가? 그렇다면 저장한다.

### 3단계: 기억 통합 (Consolidate)

1. 변경 계획을 짧은 목록으로 먼저 정리한다.
2. **사용자 승인이 필요한 변경**: 파일 삭제(병합 후 남는 중복 파일 제거 포함), 노후 판정으로 인한 삭제, 파일 3개 이상의 이름 변경이나 재배치, 색인 전면 재구성. 이런 변경은 계획과 근거를 한 번에 보여 주고 승인을 받은 뒤에 진행한다. 승인이 없으면 보류하고 보고서에 적는다.
3. **바로 진행해도 되는 변경**: 추가, 수정, 보완, 이력 기록, 색인 갱신.
4. 첫 쓰기 전에 메모리 디렉터리 전체를 백업한다.
   - 위치: `~/.claude/dreaming-backups/<project>/<YYYYMMDD-HHMMSS>/`
   - 변경할 것이 없으면 백업하지 않는다.
5. 기존 파일은 Edit로 필요한 부분만 고친다. 전체를 새 요약으로 갈아엎지 않는다. 새 파일은 Write로 만든다.
6. 마지막으로 `MEMORY.md`를 갱신한다.

### 4단계: 정합성 확인

이 스킬의 `scripts/check_memory.mjs`로 메모리 디렉터리를 검사한다. 이 스크립트는 파일을 읽기만 한다. 메모리 디렉터리 경로는 따옴표로 감싸고, Bash에서는 `C:/Users/...`처럼 `/`로 적는다.

```
{{NODE}} "{{SKILL}}/scripts/check_memory.mjs" "<메모리 디렉터리>"
```

PowerShell에서는 앞에 `&`를 붙인다.

```
& {{NODE_PS}} "{{SKILL}}/scripts/check_memory.mjs" "<메모리 디렉터리>"
```

- 출력은 `[ERROR]`, `[WARN]`, `[INFO]` 줄과 마지막 `Result: PASS` 또는 `Result: FAIL` 줄이다.
- 종료 코드: 0 = 오류 없음, 1 = 오류 있음, 2 = 인수가 틀렸거나 디렉터리가 없음.
- frontmatter가 있는 파일에 `no frontmatter` 경고가 나오면 파일 맨 앞에 BOM(UTF-8 서명)이 붙었는지 본다.

스크립트가 확인하는 항목은 아래 앞의 네 가지다. 스크립트를 실행할 수 없으면 이 네 가지를 Glob/Grep/Read로 직접 확인한다. 뒤의 두 가지는 스크립트가 보지 않으므로 늘 직접 확인한다.

- **색인 참조:** 색인의 모든 링크가 실제 파일을 가리키는지, 모든 기억 파일이 색인에 있는지(`MEMORY.md` 자신은 제외)
- **frontmatter:** 각 파일에 `name`과 `description`이 있는지, `name`이 겹치지 않는지
- **색인 크기:** `MEMORY.md`가 200줄과 25KB를 넘지 않는지
- **비밀 정보:** 비밀 정보로 보이는 문자열이 없는지
- **보존 확인:** 백업과 비교해(diff) 핵심 결정이나 교훈이 사라지지 않았는지
- **중복 재점검:** 내용이 겹치는 항목이 남아 있지 않은지

`[[name]]` 링크의 대상이 아직 없는 것은 오류가 아니다. 나중에 써 둘 만한 주제라는 표시로 본다.

### 5단계: 결과 보고

실제로 한 일만 간결하게 보고한다. 해당 없는 항목은 빼도 된다.

```
## 수면 결과
- 대상: <메모리 디렉터리>
- 백업: <경로 또는 "변경 없음">
- 새로 기록: …
- 수정: … (무엇이 왜 바뀌었는지)
- 병합한 중복: …
- 보류한 불확실 정보: … (이유)
- 승인 대기 중인 삭제·구조 변경: …
- 변경한 파일: …
- 정합성 검사: 통과 / 발견한 문제
- 처리 중 문제: …
```

정리할 것이 없으면 "새로 정리할 기억이 없어요"라고 짧게 말하고 끝낸다. 할 일을 만들어 내지 않는다.

## 4. 수면 제안 규칙 (이 스킬을 실행하지 않은 상태)

MinsuTerm은 사용자의 `CLAUDE.md`를 고치지 않는다. 그래서 수면 제안 규칙은 이 스킬 안에만 있다. 스킬을 실행하지 않는 동안 늘 보이는 것은 위의 설명뿐이므로, 핵심(작업이 끝난 뒤 한 줄로 한 번만 제안, 승낙 전에는 실행하지 않음, 거절하면 다시 묻지 않음)은 설명에도 적어 두었다.

수면이 필요해 보이면 제안만 한다.

**제안 조건**

- 큰 작업이나 프로젝트의 주요 단계가 끝났다.
- 중요한 설계 변경이나 결정이 여러 번 있었다.
- Auto Memory에 반영되지 않은 중요한 정보가 쌓였다.
- 기억의 중복, 충돌, 노후화가 의심된다.
- 사용자가 긴 작업을 마치고 세션을 마무리하려 한다.
- 컨텍스트가 매우 길어졌다. 사용량이나 압축 시점을 확인할 수 없으면 수치를 지어내지 않는다.

**제안 방식**

- 하던 작업이 끝난 시점에 한 줄로 한 번만 제안한다. 작업 도중에는 끼어들지 않는다.
  예: "중요한 정보가 많이 쌓여서 기억을 정리하고 자는 게 좋겠어요. 수면할까요?"
- 사용자가 거절하면 같은 세션에서는 다시 묻지 않는다. 그 뒤에 새로운 큰 변화가 생긴 경우만 예외다.
- 제안은 실행이 아니다. 사용자가 승낙하거나 직접 지시하기 전에는 이 스킬을 실행하지 않고 메모리를 수정하지 않는다.
- 이 규칙은 수면 실행에만 해당한다. 평소의 Auto Memory 저장 방식은 바꾸지 않는다.

## 5. 진행 스킬과 연결 (`minsuterm-progress`)

- 진행도 페이지에서 **자러 가기**를 누르면 `minsuterm-progress`가 고른 항목을 마치고 `sleep now`를 한 뒤 이 스킬을 실행한다. 이 스킬이 끝나면 진행 스킬의 `sleep done`을 한다.
- 대화에서 직접 수면을 지시받았을 때도(예: "좀 자라") 이 폴더에서 진행 보고를 하고 있으면(`progress/data.json`이 있으면) 같이 한다: 백업 전에 진행 스킬의 `sleep now`, 결과 보고 전에 `sleep done`. 그래야 진행도의 방에서 에이전트가 잠들었다 일어난다. 진행 보고를 하지 않는 폴더에서는 하지 않는다.
- 수면하는 동안에는 다른 진행 명령을 부르지 않는다. 기록을 고치는 진행 명령을 부르면 깨어난 것으로 기록된다.
- 이 스킬은 기억만 다룬다. 진행 기록(`progress/`)에는 끝난 뒤의 `sleep done` 하나만 남긴다.
